# Experiment 007 retrospective — 7 October 2026

Status: closed for design conclusions; the existing pilot remains available.
Implementation checkpoint: `0785a0a` on `xbt-agent/experiment-act-learn`.
The working tree was clean at review: implementation had already been committed
and pushed. This checkpoint publishes observed results, not uncommitted product code.

## Observation

The concept remains promising according to the user. Two barriers prevent daily
utility: waiting for a suggestion, and receiving work that may already be complete.
The user accepts short questions to update project state, but requires completion
state to be resolved before Hoomy presents an activity as something to do.

The local backend held four completed requests at capture: one v1 trial on
27 September and three v2 trials on 7 October. All used the preserved 15-project
Discover map. No new inference or feedback was submitted during this review.

The v2 median is 91.68 seconds; mean 94.29 seconds. Each request allowed five
minutes of human attention: worker wait alone consumed 26–38% of that duration.
These are worker timings, not measured click-to-paint latency. Queueing and the
UI polling interval may add delay. Remaining overhead is a subtraction, not a
measured breakdown of startup, source reading, validation or transport.
Three samples cannot support a latency percentile or a causal comparison to v1.

## What worked

- All selected v2 sources were read, improving the earlier large-source failure.
- Explicit completion confirmations persisted; successive contexts included one,
  then two facts. The five-minute constraint was recognized.
- The agent attempted generic tool-based verification without a task-specific catalog.
- Historical assumptions and access limitations were recorded rather than hidden.

## What failed

1. **Serial work remains on the user's critical path.** Each request restarts
   retrieval, generation, verification and reconsideration. A previous confirmation
   triggers the same expensive loop instead of advancing through prepared state.
2. **Unknown state is allowed through.** The first v2 verification could not access
   the authenticated source, yet its activity was presented and was already done.
3. **Verification is not bound to the final activity.** Both follow-ups selected a
   different completion claim from the one checked. A positive result for one
   candidate cannot establish the state of its replacement.
4. **The follow-up workaround hides uncertainty.** `followup_depth >= 1` forces
   `needs_confirmation = false`. This reduces visible questions without establishing
   that the activity remains undone. It must not survive into the next policy.
5. **Facts are request-based, not idea-based.** Semantic reconciliation is left to
   another LLM call. There is no stable idea identity, current state, freshness rule
   or cheap eligibility check across requests.
6. **No learning outcome is measured.** Zero performed activities have an impact/
   attention assessment. Two completion corrections demonstrate state collection,
   not improved predictions or task usefulness. Silence on the latest trial is unknown.

## Decision for the next experiment

See [experiment 008: prepared ideas and fast decisions](008-ready-ideas-decisions.md).

Prepare ideas and their evidence ahead of the interaction. Keep a persistent,
versioned state for each idea. Only ideas positively established as still pending,
with applicable evidence and satisfied prerequisites, may enter the suggestion set.
Unknown, stale, conflicting and completed ideas are excluded. Unknown state can
produce an update question or a background generic verification job, never a task
presented as ready. A model probability alone is not evidence of unfinished work.

The fast path should use local state plus compact typed decisions. The slower
Codex agent discovers ideas, investigates missing state and prepares their wording
outside the user's waiting path. Questions must be limited to one or two useful
updates, with “I don't know” and “skip” available. Proactivity follows from preparation
and state freshness; it cannot be achieved solely by making generation faster.
