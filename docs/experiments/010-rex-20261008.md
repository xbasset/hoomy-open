# Experiment 010 retrospective — 8 October 2026

Status: closed for this evaluation checkpoint; the pilot and its state remain available.
Implementation reviewed: `447255d` on `xbt-agent/experiment-act-learn`.
Predecessor: [project dialogue and research explorer](010-project-dialogue-and-research-explorer.md).

## Objective and conclusion

Hoomy should quickly suggest an activity that matters now, is still pending, and can
actually be started. Interactions should improve subsequent suggestions with little
effort from the person, eventually supporting proactive use.

The trial demonstrates persisted human context and a fast final selection. It does
not yet demonstrate a useful end-to-end activity or improved recommendations through
learning. Preparation, uncertain resources and product affordances remain barriers.

## Observed usage

The evaluation covers the user's morning tests on 8 October: six preparation requests
and one delivered activity. Earlier development replays are excluded. These records
are stages of several interactions, not seven independent task-success trials.

The interval from the explicit comparison request to the persisted activity is
**115.80 seconds**, including user response time and service processing, about 39% of
the stated five-minute window. This is not measured click-to-paint latency. The final
selector had only **one eligible idea**, plus abstention: its speed does not establish
ranking quality among several useful alternatives.

## Lessons from the evidence

1. **Context collection works.** Intent answers and the confirmation that an activity
   remains pending are distinct persisted records. The latter allows the idea through
   the readiness gate; an inconclusive agent check alone did not make it ready.
2. **Fast selection does not make the whole interaction fast.** Research and
   clarification still happen while the person waits. End-to-end latency and the
   effort of answering must remain visible alongside Decision API timing.
3. **A ready label needs an actionable destination.** The delivered instruction asks
   the user to attach documents “here”, but the activity screen has no attachment
   control. A user's “À faire et possible” confirmation cannot establish that the
   application's proposed interaction exists. Product capability is a separate
   prerequisite from task completion state.
4. **Resource uncertainty needs a precise next step.** The recorded check took
   26.06 seconds and inspected filenames, not PDF contents. It correctly retained an
   unknown state, but the subsequent suggestion asks the user to gather resources
   before establishing where they already are. A targeted location question is a
   direction to test; missing evidence does not establish missing documents.
5. **Failures waste supplied context at the point of use.** Two of six preparations
   end with `invalid_result`, including the continuation after Project A's answer.
   The answer survives in storage, but the interaction yields no activity. The logs
   identify the failing stages, not the precise rejected fields.
6. **Memory is not yet demonstrated learning.** No completed activity has a recorded
   usefulness/attention assessment. No research-graph feedback is recorded in this
   sample. Neither absence proves that the person did nothing or never opened the
   explorer. We cannot yet evaluate improvement, graph usability or daily utility.

## Checkpoint and handoff

Retain the separation between user intent, observed task state, unresolved resource
access and outcome feedback. Keep generic agent verification and the rule excluding
unknown completion states from ready suggestions. Do not equate a short-term goal
answer with a permanent project priority; the current context store selects the
latest answer per project and dimension, so its temporal scope needs attention.

The next experiment is intentionally not specified here: the user has a new direction
to explore. Carry forward one evaluation requirement: observe a complete path from
understood intent and located resources to an activity the person can start, then
capture its actual result. Measure total delay, clarification effort and confirmed
progress. Adding model or schema complexity is not itself evidence of improvement.

This checkpoint changes documentation only. Existing projects, user answers, candidate
states and trial history are preserved; no new inference or synthetic feedback was
submitted for the retrospective.
